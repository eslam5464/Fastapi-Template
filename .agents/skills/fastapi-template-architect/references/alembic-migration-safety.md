# Alembic Migration Safety

Source: `docs/backend-architecture.md` ("Alembic Migration Safety Guide") plus the real
`app/alembic/env.py` (snapshotted in `../assets/`) and `alembic.ini`.

## This repo's `env.py` — real mechanics, not generic Alembic boilerplate

- Uses an **async engine** (`create_async_engine`) and runs migrations via
  `asyncio.run(run_migrations_online())` — standard Alembic scaffolding assumes sync;
  this template's `env.py` is already adapted for the async SQLAlchemy setup, so copy it
  rather than regenerating from `alembic init`'s default template.
- `target_metadata = meta` — the same schema-qualified `MetaData` from `app/core/db.py`
  (naming convention for `pk_`/`fk_`/`ix_`/`uq_`/`ck_` constraints applies to
  autogenerated migrations too).
- `include_name()` restricts autogenerate to only the configured
  `settings.postgres_db_schema` — without this, `--autogenerate` would try to diff every
  schema visible to the connection, not just this project's.
- `do_run_migrations()` explicitly creates the schema if missing
  (`inspector.has_schema()` → `connection.execute(CreateSchema(...))`) before running
  migrations — a fresh database doesn't need a manual `CREATE SCHEMA` step first.
- `compare_type=True` and `compare_server_default=True` are both set — autogenerate will
  catch type and server-default changes, not just added/removed columns.
- `alembic.ini` uses `script_location=%(here)s/app/alembic`, a dated revision filename
  template, UTC timestamps, and a `black` post-write hook (ruff is noted as a viable
  alternative in a comment).

Migration files use the naming pattern `YYYY_MM_DD_HHMM-<rev>_<slug>.py` and live in
`app/alembic/versions/`. This directory is excluded from ruff/ruff-format in
`.pre-commit-config.yaml` — don't manually reformat generated migration files.

## Expand/contract strategy (default approach for any schema change)

1. **Expand**: add new nullable columns, new tables, or dual-write-safe constraints.
2. Deploy an app version that writes both old and new shapes if needed.
3. **Backfill** data in controlled, checkpointed batches with an idempotent script.
4. Switch reads to the new shape.
5. **Contract**: drop old columns/constraints only after verification.

Never collapse expand+contract into one migration/deploy for anything already in
production with running application code depending on the old shape.

## Migration risk matrix

| Change type | Risk | Safe pattern | Rollback posture |
|---|---|---|---|
| Add nullable column | Low | Expand directly | Simple down revision |
| Add non-null column with existing rows | Medium | Add nullable → backfill → enforce non-null later | Two-step rollback |
| Rename/drop column used by running code | High | Dual-write period, delayed drop | Requires staged rollback |
| Large table rewrite / index build | High | Concurrent/online strategy where the DB supports it | Predefined abort conditions |

## Deployment sequence

1. Preflight checks (row counts, lock sensitivity, dependent code paths).
2. Apply the expand migration.
3. Deploy the compatible app version.
4. Run backfill with checkpoints and resume capability.
5. Verify parity metrics and error rates.
6. Apply the contract migration in a later release window — never the same window as an
   expand that a rollback might still need to reverse.

## Backfill guardrails

- Chunked batches, deterministic ordering.
- Record progress checkpoints for restart safety.
- Keep each batch short to reduce lock windows.
- Emit migration telemetry: processed rows, failures, retries, duration.

## Rollback rules

- Every migration set defines explicit rollback decision points before it ships.
- Contract migrations should never ship in the same deploy step as their paired expand if
  rollback risk is non-trivial.
- If parity checks fail post-backfill, stop the rollout and revert app behavior *before*
  running the contract migration — don't contract on a failed backfill.

## Review checklist for any migration PR

- Is the change backward compatible with the currently-deployed app version?
- Is there a tested backfill plan with checkpoints?
- Are lock/timeout risks assessed for large tables?
- Are rollback conditions and an owning on-call documented?
- Are contract-phase drops deferred until post-verification?

## Commands (this repo's conventions)

Prefer the interactive wrapper scripts over raw `alembic` when working in this repo:

```bash
# Linux/macOS
./scripts/alembic.sh
# Windows
.\scripts\alembic.bat
```

Or directly:

```bash
alembic revision --autogenerate -m "Description"
alembic upgrade head
alembic downgrade -1
```
